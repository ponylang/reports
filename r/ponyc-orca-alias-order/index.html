ponylang/ponyc #6696 · fix-orca-alias-order · 8af3b8949

Fix garbage collection when a tag aliases a val or iso reference

Objects reachable through a val or iso now stay alive even when the garbage collector reaches the same object through a tag first.
10 files changed+1,152−212

Motivation

A tag gives access to an object's identity only. The collector can count the object without following its fields. Previously, that visit could also suppress field tracing through a later readable alias, leaving reachable children eligible for collection.

Behavioral Changes

The collector now honors the readable reference in either visit order. A message containing both aliases still accounts for the object once.

Architecture

Counting an object and tracing its fields

On the first visit, begin_visit records whether the reference was opaque. A later val or iso can then trigger the field tracing its capability requires. Repeated aliases add no further message credit.

When an opaque visit borrows reference-count credit for a remote object, a later val updates the pending acquire with the object's type and immutability. The actor borrows only once. If it already held credit before the loan, it also traces the fields to protect them until the owner receives the acquire.

Looking up the owner

To find the heap chunk and its owning actor, each thread caches the last leaf it found in the pagemap. Addresses in that leaf share the walk down the tree. Each lookup still reads the chunk and owner from the entry for that address, so clearing or reusing an entry takes effect on the next lookup.

Regression tests

The runtime tests check alias order during send, receive, and remote marking. They also check that a self-send pins an object once per message, that the owner receives immutable credit, and that old visit marks expire. The pagemap test switches among addresses and checks both the chunk and the owner on every lookup.

Release Notes

Fix garbage collection when a tag aliases a val or iso reference

A Pony program could crash when an actor used data it had received in a message. If the message contained both a tag and a val or iso reference to the same object, the garbage collector could free data reachable through that object's fields before the receiving actor used it. The runtime now keeps that data alive while the actor can still reach it.
